![alt text](screenshots/01-laravel-build.png)
PHP-FPM отделяет выполнение кода от веб-сервера, позволяя Nginx эффективно отдавать статику и масштабировать приложение. Это производительнее и архитектурно чище монолитного Apache+mod_php в контейнерной среде.

![alt text](screenshots/02-composer-layer.png)
Копирование всего проекта до установки зависимостей сбрасывает кэш Docker, заставляя заново запускать тяжёлый composer install при любом изменении файла. Раздельное копирование manifest-файлов сначала позволяет кешировать слой с библиотеками, ускоряя повторные сборки.

![alt text](screenshots/03-dockerignore.png)
Попадание .env в образ раскрывает пароли и секретные ключи любому, кто получит доступ к образу. Исключение файла через .dockerignore гарантирует, что конфиденциальные данные остаются только на хосте или передаются через безопасные переменные окружения.

![alt text](screenshots/04-requirements.png)
Фиксация версий гарантирует воспроизводимость сборки и защищает от поломок из-за обратно несовместимых изменений в новых релизах. Использование latest через год может привести к неработоспособности приложения из-за скрытых обновлений зависимостей.

![alt text](screenshots/05-fastapi-build.png)

![alt text](screenshots/06-uvicorn-cmd.png)
Адрес 0.0.0.0 заставляет сервер слушать все интерфейсы контейнера, делая его доступным для внешних подключений. Если указать 127.0.0.1, сервис будет доступен только внутри самого контейнера, и запросы от Nginx будут отклоняться.

![alt text](screenshots/07-nginx-conf.png)
Docker автоматически резолвит имена сервисов из compose-файла во внутренние IP-адреса через встроенную DNS-систему. Использование имени laravel вместо 127.0.0.1 обеспечивает стабильную связь между контейнерами даже при смене их динамических адресов.

Без именованного тома mysql_data все данные базы удалятся при остановке контейнеров, так как они хранятся во временном слое. Именованные volumes сохраняют данные независимо от жизненного цикла контейнера, в отличие от bind-mounts, привязанных к путям хоста.

![alt text](screenshots/11-healthcheck.png)
Обычный depends_on ждёт только запуска процесса, а не готовности сервиса, что приводит к ошибкам подключения (race condition). Использование condition: service_healthy гарантирует, что приложение начнёт работу только после полной инициализации БД.

![alt text](screenshots/12-init-sql.png)
![alt text](screenshots/13-databases-created.png)
Скрипт init.sql выполняется только при первом создании тома, так как MySQL проверяет наличие файлов инициализации только в пустой директории данных. Изменение файла после первого запуска не повлияет на базу, требуя ручного вмешательства или пересоздания тома.

![alt text](screenshots/14-env-compose.png)
![alt text](screenshots/15-env-laravel.png)
Разделение .env позволяет хранить секреты хоста отдельно от конфигурации приложения, а имя сервиса mysql вместо 127.0.0.1 обеспечивает корректную маршрутизацию внутри Docker-сети.

exec выполняет команду в уже запущенном контейнере, сохраняя его состояние, тогда как run создаёт новый временный контейнер. Для миграций критически важно использовать exec, чтобы изменения применились к текущему рабочему экземпляру приложения.

Флаг -v принудительно удаляет все именованные тома, что приводит к безвозвратной потере всех данных баз данных. Его опасность заключается в случайном стирании продуктивной информации при попытке просто «очистить» среду разработки.

![alt text](screenshots/24-logs.png)
Централизованные логи Docker агрегируют вывод всех сервисов в единый поток с метками времени, упрощая отладку взаимодействий. Это удобнее, чем переключаться между разными файлами на хосте, особенно при распределённой архитектуре.

![alt text](screenshots/25-fresh-install.png) перед началом создания скринов всё перенёс в чистое окржуение к себе на wsl
Для развёртывания достаточно выполнить git clone, настроить .env и запустить docker compose up -d --build. Эта команда автоматически соберёт образы, создаст сеть и запустит все сервисы в фоновом режиме.
